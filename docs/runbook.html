weboptions runbook

jimbrownhome

What is running

One Node process. It serves the built React app and the API from the same port, so there is no proxy, no second server and no CORS to get wrong. Everything below assumes that.

Process node backend/dist/server.js
Port 5057, on every interface, so the LAN reaches it
Started by Task Scheduler, at boot, running whether or not anyone logs in
Secrets .secrets\weboptions_ro.password, read by the launcher, never in the repo
Logs .run\weboptions.log
Database Azure SQL webportfolio, login weboptions_ro, SELECT only
Timezone Pinned to America/Los_Angeles. Week boundaries are machine-local, so an unpinned box silently shows the wrong week.

Is it healthy

Yes, /readyz exists. It is the one to use. /healthz only proves the process is answering, which it will keep doing happily while the database is unreachable. 

curl http://jimbrownhome:5057/readyz

On the server itself, use 127.0.0.1, never localhost. The server binds 0.0.0.0, which is IPv4 only, and Windows resolves localhost to the IPv6 ::1 first. Nothing listens there, so you get "Unable to connect to the remote server" from a server that is running perfectly and serving other machines.

Answer Means
200{"status":"ok","database":"ok"} Healthy, and more than it looks. That check reads a row from opt.api_key, so it proves the server is reachable, the login works, the schema is deployed and the grants are still in place.
503database_unreachable The process is fine, SQL is not. Check the network first, then whether Azure SQL is up. Also expect this for a second or two right after a restart, while the connection pool warms. Retry once before believing it.
503database_login_failed The password in .secrets no longer matches the login. Nothing else produces this.
no answer The process is down. Restart it, then read the log.

From a browser, the app tells you the same thing in words. A dead server reads Cannot reach the Web Options server, a rejected login reads the database rejected its login, and a bad key reads That key was rejected. Those are deliberately three different messages.

Start, stop, restart

All manual, by decision. Nothing auto-restarts on crash.

Start-ScheduledTask -TaskName WebOptions
Stop-ScheduledTask  -TaskName WebOptions
Get-ScheduledTask   -TaskName WebOptions | Get-ScheduledTaskInfo

If the task says it is running but the port is not, the process died without the task noticing. Find and kill the listener, then start the task again. 

Get-NetTCPConnection -LocalPort 5057 -State Listen |
    Select-Object -First 1 -ExpandProperty OwningProcess |
    Stop-Process -Id { $_ } -Force

Update: pull and rebuild

The build is not committed, so a pull alone changes nothing that is running. Every update is these five steps, in this order. 

cd C:\Files\Dev\main\weboptions
Stop-ScheduledTask -TaskName WebOptions

git pull
npm ci                 # npm install if you want to allow lockfile drift
npm run build          # shared -> backend -> frontend, in that order

Start-ScheduledTask -TaskName WebOptions
curl http://127.0.0.1:5057/readyz

npm run build is the whole thing. It compiles shared first because both other workspaces import it, then the backend, then Vite bundles the front end into frontend\dist. That last folder is what the server hands to the browser.

Run the migrations only when the numbered SQL changed. Check database\migrations in the diff. If it did, run npm run migrate with operator credentials, not the read-only login, and do it before starting the task.

Sanity check after every update: /readyz returns ok, the front page lists this week's signals, and a deep link like /calendars/2026-08-10 loads on its own rather than 404ing. That last one catches a broken static build, which is otherwise invisible until someone bookmarks a page.

The Task Scheduler entry

The task runs a launcher script rather than node directly, because it has to read the password out of .secrets and set the timezone first. Register it once, from an elevated shell, signed in as the account that owns the checkout. 

npm run install-task -- -Start

That registers but does not start, because npm swallows -Start as one of its own config flags. To register and start in one step, call the script directly: 

pwsh -NoProfile -File scripts/install-task.ps1 -Start

Re-running that is safe, and it is the fix when the task has drifted. It registers this. Note the -Force: without it, re-registering an existing task fails with "cannot create a file when that file already exists". 

$pwsh = (Get-Command pwsh).Source

$action  = New-ScheduledTaskAction -Execute $pwsh `
    -Argument '-NoProfile -NonInteractive -WindowStyle Hidden -File C:\Files\Dev\main\weboptions\scripts\serve.ps1' `
    -WorkingDirectory 'C:\Files\Dev\main\weboptions'
$trigger = New-ScheduledTaskTrigger -AtStartup
$set     = New-ScheduledTaskSettingsSet -MultipleInstances IgnoreNew `
    -ExecutionTimeLimit ([TimeSpan]::Zero) -RestartCount 0
$principal = New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME" `
    -LogonType S4U -RunLevel Limited

Register-ScheduledTask -TaskName WebOptions -Action $action -Trigger $trigger `
    -Settings $set -Principal $principal -Force

ExecutionTimeLimit of zero matters. The default kills a task after 3 days, which would look exactly like a random unexplained outage.

A PowerShell window that opens at boot and stays open means the task was registered with an Interactive logon type, or through the GUI with "run only when user is logged on". That draws the launcher on your desktop, and the launcher holds the console for as long as node runs, so the window never closes. Closing it kills the server. Re-run npm run install-task to put it back on S4U, which has no desktop to draw on. -WindowStyle Hidden alone does not fix this.

Do not run this task as SYSTEM. Node is installed per user here, by Scoop, so it sits on the user PATH and not the machine PATH. SYSTEM cannot see it, and the task dies before the launcher gets far enough to say why. S4U runs it as you without storing a password, so it resolves node exactly as it does when you run it by hand. Both absolute paths above are deliberate for the same reason: pwsh may also be a per-user install.

The launcher sets the environment and then runs node in the foreground:

Variable Value
DB_SERVER sqlgkhw25ijhyzzy.database.windows.net
DB_NAME webportfolio
DB_USER weboptions_ro
DB_PASSWORD read from .secrets\weboptions_ro.password
WEBOPTIONS_WEB_ROOT frontend\dist. Without it the API runs but serves no app. Point it at a folder with no index.html and the process refuses to start, which is on purpose.
TZ America/Los_Angeles

scripts\serve.ps1 checks the build and the password file before it starts anything, so a missing npm run build fails with a sentence about it rather than booting an API with no app. The same script backs npm start, which is how you run it by hand.

Logs

Everything goes to .run\weboptions.log: one line per request from morgan, the listening address and timezone at startup, and any failure classified by the error middleware. Nothing sensitive is written. Connection strings and driver internals are deliberately kept out. 

Get-Content .run\weboptions.log -Tail 50
Get-Content .run\weboptions.log -Wait          # follow live
Select-String -Path .run\weboptions.log -Pattern '\[weboptions\]'   # failures only

There is no rotation. A single-user LAN app writes very little, but the file grows forever, so truncate it when it gets annoying. Nothing reads it back.

Keys

A key looks like woak_ plus 48 characters. Only its hash is stored, in opt.api_key, so the value appears once at mint time and never again. It is typed into the browser once and kept in local storage under weboptions_api_key. 

npm run keys -- --list
npm run keys -- --mint "iPad"
npm run keys -- --revoke 3

These need operator credentials, since weboptions_ro cannot write. Revoking takes effect on the next request, and that browser drops back to the unlock prompt.

The read-only SQL password does not rotate on a schedule. If it is ever changed, update .secrets\weboptions_ro.password and restart. /readyz will say database_login_failed until you do.

Backup

Four things exist. Only two of them actually need protecting.

Thing Verdict
back up .secrets The only thing here that is not in git and cannot be regenerated by reading something else. Two files, a few hundred bytes. Copy them somewhere encrypted and off this machine, and copy them again whenever they change, which is almost never.
back up The ingested calendars opt.calendar_week, calendar_day, calendar_trade. This is the one genuinely irreplaceable dataset, since it came from newsletters you no longer hold. It rides along with whatever already backs up the webportfolio database. Confirm that, then stop worrying about it.
skip opt.api_key Hashes only. Losing them costs one command and re-typing a key on each device. Not worth a backup policy.
skip Migrations and fixtures Both are in git and pushed to GitHub. The golden fixtures matter historically, but they are committed, so they are already backed up twice.

In short: copy .secrets off the box, confirm the Azure SQL database is in a backup you trust, and everything else restores from git clone plus npm run migrate.

When something is wrong

Symptom Look here first
Nothing answers on 5057 Process is down. Start-ScheduledTask, then read the tail of the log for why it stopped.
Log says did not start: Missing ...\backend\dist\server.js The build outputs were wiped, usually by a git clean -xdf, which takes backend\dist, frontend\dist, .run and node_modules with it. Run npm ci then npm run build before starting the task. If tsc is not recognized, that confirms node_modules went too.
Log file .run\weboptions.log does not exist serve.ps1 writes a line before it does anything else, so a missing log means it never ran. The task did not launch, rather than the app failing.
Page loads, no data, says it cannot reach the server The static files are being served but the API is not answering. Almost always means a stale frontend\dist against a stopped process. Check /readyz.
Blank page, API works WEBOPTIONS_WEB_ROOT is unset or the build did not run. Rebuild and restart.
Deep links 404, front page fine The SPA fallback is not running, which means the app is being served by something other than this process.
Wrong week showing Timezone. Confirm the startup line in the log says America/Los_Angeles.
Everything asks for a key again The key was revoked, or browser storage was cleared. Mint a new one and paste it in.
