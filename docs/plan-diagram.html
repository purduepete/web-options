weboptions — Refactor Plan

v6.1 · converged

Python Flask on the laptop becomes a Node/React app on jimbrownhome, reading from the shared webportfolio Azure SQL database. Reviewed across five rounds by Gemini 3.1 Pro, GPT-5.5 and MAI-Code-1.1 until all three returned SHIP.

1 · Phase dependency graph

Ten phases. Only Phase 4 floats free of the critical path; Phase 8 is the gate where nothing is deleted until parity against the captured Flask output is proven.

  • Phase 2 is the first irreversible step. It creates the opt schema and the weboptions_ro login on the shared production database.
  • Phase 8 deletes nothing until parity passes against golden JSON captured from the running Flask server.

2 · Runtime architecture — the write/read split

The load-bearing rule. Two different SQL principals: the laptop writes as purduepete, the service reads as weboptions_ro. The running server physically cannot write — not by convention, by permission.

  • Gemini and GPT-5.5 independently flagged the same gap: a CI grep for INSERT/UPDATE/DELETE is not a control. It is defeated by casing, string building or EXEC, and does nothing at runtime.
  • So the split moved into the database. The grep survives as a cheap tripwire, not as the fence.
  • Nothing in dbo is ever modified — it stays the webportfolio app's data.

3 · Calendar data path — before and after

The OneDrive dependency is not being removed for tidiness. It is the single thing that made the whole plan impossible on a separate host: a home server cannot read a folder that only exists on the laptop.

  • Re-ingest is one statement. DELETE FROM opt.calendar_week WHERE publish_date = @d, with ON DELETE CASCADE down to days and trades, then reinsert — all in one transaction.
  • Without the cascade the delete throws an FK violation. Gemini caught that one.
  • The extractor is backfill-only. The server never imports it, and there is no runtime HTML fallback.
