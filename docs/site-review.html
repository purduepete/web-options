weboptions — Site Review

steps 0 and 3 complete · step 1 all but the runbook

Seven pages, seven routes, 293 passing tests. Reviewed on three axes: against webportfolio, for internal consistency, and for what the roadmap actually needs. 24 findings. Two independent reviews, GPT-5.5 and MAI-Code-1.1-Flash, both returned APPROVE-WITH-CHANGES and both moved the same item to the front of the queue.

What the review changed

My draft put the UI cleanup first and the migration last. Both reviewers rejected that order for the same reason, without seeing each other's answer.

  • The Flask baseline gets frozen first. The old server is still live and still hardcodes port 5057, the port the Express backend wants. Every week both stacks coexist, the parity target drifts. Capture the golden JSON before touching another line of React, or Phase 8 is measuring against a moving reference.
  • Failure states outrank cosmetics. A revoked key, an unreachable database, a stopped API and a genuinely empty week currently all look similar. That is worth more than a shared heading component.
  • My page-contract test was wrong. I proposed asserting every route renders exactly one non-empty h1. Two pages deliberately render an empty one while loading, which is the behaviour I committed this morning. The contract should be about behaviour: one landmark, a real accessible name once loaded, errors announced, title and focus updated on navigation.
  • Six items were cut outright as over-built for a 7-page single-user local app. See the cut list below.
  • The whole operations story was missing. Neither my draft nor the phase diagram says how jimbrownhome starts the app after a reboot, where the logs go, how credentials rotate, or what gets backed up.

The revised order

Six steps. Step 0 is the one that unblocks everything else, and nothing after it is safe to start until the fixtures exist.

Step 1 · Failure states and operations

The part both reviewers said was missing entirely. For an app that lives on one box in the house, this is what "ready" actually means. Four of the seven are built; the two operations write-ups need decisions only you can make.

Work Why
done Five distinct failure messages Bad or revoked key, SQL login rejected, SQL unreachable, API process down, and a genuinely empty week are five different problems. One generic error wastes an evening later.
done A readiness check that touches SQL /healthz only proves the Node process is alive. It says nothing about whether weboptions_ro can still connect or still holds its grants.
dropped Unauthorized handling on the settings pages Both pages turned out to be static: they read the identity the provider already holds and fetch nothing. There is no request to fail. The gap was really in the key prompt, which called a key bad whenever anything went wrong, and that is fixed.
done Safe-area insets No env(safe-area-inset-*) anywhere, on an app used on iPad and phone with three stacked sticky layers.
needs you The jimbrownhome runbook Startup after reboot, where secrets live, the log path, how to restart, how to tell it is healthy, and what to do when it is not. None of that can be invented for you.
needs you Rotation and backup, written down How the read-only SQL password rotates, how an API key is minted and revoked, and what gets backed up: .secrets, opt.api_key, migration history, the golden fixtures.
done Delete /calendars The index route, page, CSS and tests came out. Latest Calendar plus the arrow keys already walks the whole archive, so a second way in earned nothing.
  • The dev proxy was hiding the very state this was for. Vite answers a refused connection with a 500 of its own, so "the API is not running" arrived looking like a bug in the API. This one only answers JSON, so an error body that is not JSON is now read as the server being down. Confirmed by killing the process: the page says so in words, and keeps the key.
  • One query covers four things. /readyz reads a row from opt.api_key, which proves in a single round trip that the server is reachable, the login works, the schema is deployed and the grants are still there. /healthz is left alone as pure liveness, since that is what a service manager wants.
  • Driver codes are classified rather than pattern-matched on message text. ELOGIN means a rotated password and says so; the socket and timeout codes mean the database is out of reach. Anything else stays a 500, so an outage and a mistake never blur.
  • The insets use max() against the design value, not the raw env(). On a device with no inset the naive version would have dropped the gutter to nothing. Asserted in safe-area-css.test.ts, since jsdom has no notch to render.

Findings I raised that are not actually problems

  • No charts is a roadmap dependency, not readiness debt. Both reviewers said so independently.
  • The toast system being called once is not a smell. Toasts should be rare in a read-mostly dashboard.
  • Title case in the menu versus sentence case in headings is a choice, not an error. Menu labels can reasonably differ from page headings.
  • .signals-error used across pages is naming debt, not functional debt. Worth fixing while nearby, not worth a dedicated slot.

The two reviews

Different families, per the review policy: primary Claude Opus 5, reviewed by GPT and MAI. Neither saw the other's answer.

APPROVE-WITH-CHANGES

GPT-5.5

"The order is too UI-cleanup-heavy before the migration risk is retired. Every new React/Node change made while Flask is still live increases the chance that parity becomes a moving target." Also caught that the page-contract test conflicts with the deliberate empty loading heading, and argued the whole local-operations story was absent: "production ready mostly means you can restart it on the home box, rotate credentials, recover config, and know why it is blank."

APPROVE-WITH-CHANGES

MAI-Code-1.1-Flash

"The sequence is wrong in one important way." Same conclusion, reached separately: freeze the baseline first, because coexisting stacks on one port mean "your comparison is compromised and your plan is invalid." Called the feature-before-migration ordering basic project hygiene rather than architecture, and flagged the same missing operations work: backup, rollback, observability, credential rotation, and a real jimbrownhome install story.
